Load path

Reads the "Export Load Path" pyRevit button's output — traces each column/wall down through the model's physical geometry (columns, walls, beams, footings) to the footing it lands on, flags any that don't connect all the way down, and estimates a rough gravity load per footing from a simple nearest-neighbor tributary area × each level's own dead/live load, set per level below. Not a substitute for a real structural analysis.

Level loads▾

Dead and live/snow load per level, read straight off your General Notes sheet — one row per level found in this project's export, roof levels called out separately. Applied per-member by its own level: a column's footing load sums each story's own DL+LL x tributary area, not one blanket number for the whole building. Used by the Footings table below (for both column point loads and, using the wall tributary width above, wall line loads on continuous footings) and the Beam / Joist Check. Values are remembered per project/level in this browser.

Broken / unresolved load paths▾

These columns or walls don't connect down to a footing within the search tolerance — could be a real modeling gap, or just this tool's endpoint-matching missing an unusual connection. Worth a visual check in Revit either way.

Isolated (bearing) footings▾

Column loads only — each connected column's own tributary load, summed per footing. Wall loads never contribute here.

Continuous footings▾

Wall loads only, per linear foot — column loads never contribute here. Which table a footing appears in is decided by the footing's own type/geometry (isolated pad vs. continuous strip), not by which load traced to it — foundation slabs are excluded entirely. A column load that traces to a continuous footing, or a wall load that traces to an isolated pad, is flagged in the summary above as a likely trace mismatch worth checking manually, rather than pulled into this table. Each wall's tributary width is computed from your actual modeled floors (not a single typed-in number) — the "Wall tributary width fallback" field above is only used where that couldn't be computed.

Beam / Joist Check▾

Flags modeled beams/joists that look undersized for their span, reusing the same bending/shear/deflection math as the LVL/I-Joist Calc tab. Tributary width here is a single value applied to every member (this project's typical joist/beam spacing) — not read per-member, so treat this as a first pass, not a per-beam design check. A member whose size couldn't be parsed from its family/type name is flagged rather than guessed. Open Web Wood Joists (OWWJ) are assumed to bear only at their two ends — they are never flagged as multi-span continuous, even if a column happens to sit under the middle of one.

Dead/live loads come from the Level loads table above — each beam/joist uses its own level's values. Tributary width is measured per-member from the modeled spacing to its nearest parallel neighbor on the same level (half-distance each side) — the fallback below is used only when no neighbor running alongside a member can be found.

Tutorial — sizing a simple deck

A worked example walking Beam Sizing, Joist Spans, Section Properties, and Footing Sizing together on one real deck, so you can confirm the tools' numbers match a hand check.

The example project

A simple ground-level deck, 12 ft wide (along the house) by 10 ft deep: a ledger bolted to the house on one side, a beam on 3 posts at the outer edge (2 end posts + 1 mid post, so the beam is really two 6-ft bays, not one 12-ft span), and joists spanning between the ledger and the beam.

Plan view — ledger at top, beam on 3 posts at bottom, joists spanning between them. The beam only picks up half the joist span (the ledger/house carries the other half), so its tributary width is about 5 ft, not the full 10 ft.

1 · Beam Sizing — the beam (a mid-post changes the answer a lot)

Enter: preset Deck (DL 10 / LL 60) · width 5-1/2" · Bay span(s): "6,6" (this is the field to watch — NOT "12", since the mid post breaks the beam into two 6-ft spans) · tributary 5 ft · Fb 2400 · E 1.8 · L/360.

w = (10+60) × 5 = 350 plf per bay  ·  each 6-ft bay: M = 350 × 6²/8 = 1,575 ft-lb  ·  Sx req = 1,575×12/2400 = 7.9 in³  ·  I req = 28.4 in⁴

Tool's answer for "6,6": 5-1/2" x 6" — a much smaller beam than the 5-1/2" x 9" a (wrong) single 12-ft span would call for. Treating the mid post as if it weren't there is the single easiest way to over-order material on a deck this size — or, read backwards, entering "6,6" instead of "12" is the check that catches it. (Beam Sizing itself now handles a point load partway along a bay via its own point-load fields, alongside the multiple-bay diagram — the LVL/I-Joist Calc tab is only needed for an LVL or engineered I-joist member.)

Each bay is checked as its own simple span (the multi-span input takes the worst bay) — that's conservative versus true continuous-beam behavior, not unconservative. Also: the L/360 deflection check uses combined dead+live load, not live load alone, which is slightly conservative in the same safe direction.

2 · Joist Spans — the joists

Set: Grade No. 1 · preset Deck (DL 10 / LL 60) · deflection L/360. For a 10-ft joist span, No. 1 2x8 @ 16" o.c. now shows a noticeably shorter allowable span under the deck's 60 psf live load than it does on the Residential Floor (40 psf) preset — still enough for our 10-ft span, but worth watching on a longer or more tightly-spaced layout. Switch the preset back and forth and watch the same row change — that's the whole point of these being inputs now instead of a fixed table.

These spans come from standard NDS-style Fb/E values with a repetitive-member factor, checking bending and live-load deflection only (no shear, no bearing) — they'll be close to, but won't exactly reproduce, a specific published AWC/IRC table. Still confirm against the adopted code table before it goes on a drawing set.

3 · Section Properties — the cross-check

No inputs here — just Sx and I generated from geometry, so you can verify what Beam Sizing handed you:

Sx = b·d²/6 = 5.5×6²/6 = 33.0 in³  ·  I = b·d³/12 = 5.5×6³/12 = 99.0 in⁴

Filter Width to 5-1/2" and find the 6" row — it should read Sx 33.0, I 99, matching the Beam Sizing tool's "provided" numbers for the "6,6" case exactly. If those two tabs ever disagree, that's a real bug worth reporting.

4 · Footing / Bearing — the posts

Beam Sizing's own "Send to Footing" button (next to each support reaction) can carry this over automatically now, but by hand: with w = 350 plf and 6-ft bays on each side of the mid post, the end posts each pick up roughly 350×6/2 = 1,050 lb, and the mid post picks up both adjacent half-bays: 350×6/2 + 350×6/2 = 2,100 lb (2.1 kips — this tab takes load in kips, not lb).

Set: mode Size a footing · type Isolated / Spread · shape Square · P 2.1 kips (the mid post, worst case) · e = 0 · qa 1,500 psf.

Tool's answer: 1'-3" x 1'-3" square footing (1.6 ft²), qmax = 1,344 psf against the 1,500 psf allowable — hand-checked (P/qa = 2,100/1,500 = 1.4 ft² → ~1.18 ft side, rounded up to the nearest inch) and it matches. Note this tool doesn't apply a code-minimum footing size floor the way some jurisdictions require (commonly 18"+ regardless of load) — that's on you to check separately, same as frost depth.

Service-level loads only, no concrete design (shear/flexure/reinforcing), no footing self-weight added automatically, uniaxial eccentricity only. Always confirm frost depth and the locally adopted minimum footing size for La Grande / Union County.

Using this as your own check, going forward

  1. Sketch the framing first and count the actual supports — a mid post means two bays, not one span. This is the mistake that costs the most material if missed.
  2. Work out w, M, and Sx required by hand for your actual span/tributary/load before opening the tool.
  3. Confirm the tool's "required" lines match your hand calc almost exactly.
  4. Cross-check the "provided" Sx/I against Section Properties for that width/depth.
  5. Hand-carry the beam's post reactions (in kips) into the Footing tab — there's no automatic link between the two tabs.
  6. Still run anything going on a drawing set past a stamped calc or the EOR — these tools are preliminary field checks, not a substitute.

Notes

All the caveats, assumptions, and code-basis notes from every tab, collected here. Each calculator links back to its own section with a "See Notes" link instead of carrying the full paragraph inline.

Beam Sizing

Point loads above are optional and superposed onto whichever bay/overhang they fall in. Each bay, and each overhang, is checked as its own independent case (a bay as a simple span; an overhang as a cantilever, M=w·a²/2 at the support) and the worst one sizes the whole beam — that's conservative versus a true continuous-beam analysis (a real continuous beam usually sees lower span moment near a cantilevered end), not unconservative, but it will occasionally call for more beam than a continuous-beam calc strictly requires. Post vs. Wall is a label only in the diagram — it doesn't change this calculation; a wall (continuous) support in reality shares load differently than a discrete post, which matters for a real bearing/hanger design even though it doesn't change the beam's own bending/deflection check. Width is fixed by your selection above (or your custom entry) — the calculator solves only for the required depth at that width; it will not swap you to a different width to save material. Default is 5-1/2", Tamarack's typical beam width. Note two separate glulam width families exist: 5-1/2"/7-1/2"/9-1/2" are the Southern Pine series, manufactured net-width to match dimension lumber (flush with a 2x6/2x8/2x10 wall or post); 3-1/8"/5-1/8"/6-3/4"/8-3/4" are the Western species (Douglas Fir) series, which do NOT match dimension lumber widths. A custom width/Fb/E lets you check a sawn timber, LVL, PSL, or a glulam width/grade not in the lists above — Sx/I are still generated from simple rectangular geometry (b·d), so this isn't valid for a non-rectangular or built-up unequal-ply section. The species/grade picker for custom Fb just fills in typical dimension-lumber base values (No. 1/No. 2 unless noted) as a starting point — confirm the actual grade stamp and current NDS Supplement value for your specific size before specifying, since large-timber (beam & stringer) reference values differ from dimension-lumber values. Confirm which series your supplier stocks before specifying. Verify bearing, lateral-torsional buckling (CL), and connection design separately. Support reactions shown below the beam are simple-span/cantilever reactions per this beam's own loads only — they don't include the beam's self-weight or anything stacking on top of that post elsewhere in the structure, so add those before sizing a footing.

LVL / I-Joist Calc

Assumes simple span, load at midspan for the point load, superposition of uniform + point load effects. Sawn lumber and LVL values are representative base design values (no CD/CM/CL/CF adjustment applied) — treat as a starting point, not a final design. I-joist depths are picked from generic representative capacities, not a specific product line.

Joist Spans

Calculated from standard NDS-style Fb/E design values for DF-L (with size factor CF and a 1.15 repetitive-member factor, since these span/size checks assume joists spaced ≤24" o.c.), checking bending and live-load deflection only — shear and bearing at supports are not checked here, same as the Beam Sizing tab. Each bay and overhang above is checked independently (bay = simple span, overhang = cantilever from its bearing), and one common size is suggested that satisfies all of them at once — the worst bay or overhang governs. These will not exactly match a specific published AWC/IRC span table (which may use slightly different reference values), so still confirm against the current adopted IRC/AWC span tables and Oregon amendments before use in a drawing set. Also remember: if your load case isn't a plain floor (a deck at 60 psf, for instance), you must change the Dead/Live load fields above — they do not update automatically from context. Sizes checked run 2x6 through 2x14; if nothing that size works, look at an LVL/I-joist on the LVL/I-Joist Calc tab instead.

Footing / Bearing

Service-level (unfactored) loads only — this sizes/checks soil bearing pressure against an allowable value you provide, it does NOT check concrete design (one-way/punching shear, flexure, or reinforcing) or overturning/sliding. Footing self-weight and any soil surcharge above the footing are NOT added automatically — fold them into the load you enter if you want them reflected. Eccentricity is uniaxial (one direction at a time, computed by e=M/P) — a footing with real biaxial eccentricity needs a full two-way check, not this tool. When e exceeds the kern (L/6 or W/6), the soil is assumed to lift off part of the footing and pressure is redistributed as a triangular block over the remaining bearing length — a condition worth avoiding under sustained loads even if the sized/checked qmax still passes; sizing mode rounds the solved dimension UP to the nearest inch, so the actual qmax at that rounded size is always at or slightly under qa, never over. The allowable bearing value is whatever you type in qa — the Site Data (ZIP) tab can hand you a rough regional placeholder as a starting point, but always confirm the real number against the project's actual geotechnical report before finalizing a footing size.

Site Data (ZIP)

Values are coarse 3-digit-ZIP regional estimates, not a site-specific hazard report. Ground snow load in the Cascades/Rockies foothills and the eastern Idaho/Yellowstone corridor is strongly elevation- and fault-proximity-dependent — always confirm snow against the state/county-adopted snow load map (SEAO for Oregon; local jurisdiction maps for WA and ID) and confirm wind/seismic against the ASCE 7 Hazard Tool (asce7hazardtool.online) before finalizing a design. Coverage: Oregon (970–979), Washington (980–986, 988–994), and Idaho (832–838) 3-digit ZIP prefixes. Elevations are regional-default (largest city/town in that prefix) — always enter the actual site elevation above when you know it, since it drives the snow load estimate directly.

Load Path

This traces load paths GEOMETRICALLY — matching analytical member endpoints against each other within a small tolerance — because the current Revit Structural Analytical Model API doesn't expose a direct "what supports this" query (confirmed against Autodesk's own API docs/forums, not assumed). It will read ordinary end-to-end framing correctly but can miss or misjudge unusual conditions: offset connections, transfer members, anything not geometrically coincident at a shared point. Tributary area is a simple nearest-neighbor half-distance estimate per column (like a quick hand sketch), not a true tributary-polygon solve — rougher on irregular or transfer framing, and NOT computed for walls (continuous footings show connectivity status only, no accumulated load). Required footing size uses simple average bearing (P/A, no eccentricity) — it does not read the actual size of the footing family already in your model, and does not check concrete design, overturning, or sliding. Confirm anything this flags against the actual model and a real structural analysis before relying on it.

PDF Compare

Pages align by the page NUMBERS you set above, not by title block or sheet number — if a sheet was inserted or removed mid-set, the two page numbers will drift out of alignment further into the set. Step pages independently on each side to re-sync. On render resolution: a literal 600 DPI render of a full 24"x36"+ sheet is roughly 20,000+ pixels wide — no browser canvas or in-browser pixel diff can hold or process that without crashing the tab. "Maximum" renders at 4000px, which is the highest width this tool can diff at interactively; on a 30"-wide sheet that's about 130 DPI on-screen, and combined with scroll-wheel zoom (up to 6x) gives you well beyond 600 DPI of effective magnification once you're zoomed into a detail — the rendered pixels are just being magnified further, same as zooming into any raster image. For true pixel-level, print-resolution inspection of one specific area, download the current view as PNG and open it in an image viewer at 100%.

Detail Catalog

Getting details OUT of Revit is fully automatic — that part never needs Insert Views from File or any hand-typing. You can still add, edit, or delete a catalog entry right here in the browser too, for anything not worth round-tripping through Revit (a "My Catalog" entry, tagged read-only-safe from the synced ones so a re-sync never touches it). Sync Detail Library is created once (a brand-new Details Library.rvt) and then reused on every later run — it walks a folder of your regular projects, and any project whose file hasn't been saved since the last run is skipped without even opening it, so most runs only touch what actually changed. For a changed project, it pulls in every drafting view that's actually placed on a sheet (its own definition of a "real" detail) AND every legend view outright (legends need no sheet-placement test — they're deliberate by nature), updates an entry in place if you revised it, and keeps both versions side by side if a same-named entry from a different project turns out to have different content. It also tags each detail's Foundation/Floor/Roof/PEMB sheet type from the sheet(s) it's actually placed on — a detail on a "Foundation Details" sheet is a foundation detail even in a PEMB project, checking the sheet name first and falling back to the project name/notes only when no sheet says anything — tagging legends simply "Legend"; use the "Sheet type" filter above to narrow by any of these. It also guesses Element/Material/Connection (Column, HSS, Bearing, and so on) straight from each detail's own view name so you can browse or filter by type — HSS, timber, moment connection, whatever — and remembers which project (and sheet, for a detail) each one was actually pulled from, shown right on the card and inside its own modal as "Pulled from…". Legends have one real Revit limitation: the API can duplicate an existing legend but can't create one from nothing, so both the library and whatever project you're pulling a legend INTO need at least one legend view already sitting in them (even a blank one, made once by hand via View → Legends → Legend) before a legend can sync or place. It writes detail-catalog-export.json itself at the end of every run (no separate step needed), which this tab only ever reads. The older Build Detail Database button still works for a quick refresh if you only changed something in the library by hand. Search is tokenized and ranked like a real search engine — every word you type has to match something (name, view name, element, material, connection, sheet type, tags, source project/sheet, or description), and a hit in the name ranks above one buried only in the description, so a two-or-three-word search narrows in fast without needing an exact phrase. Open a card and click "Place on sheet" to drag a marker onto roughly where it should land — that writes a placement request to detail-catalog-pull.json in the same linked folder, and that card then carries a red "Queued" badge (in the grid and inside its own modal, which lists exactly which project/sheet it's queued for) until "Import Queued Details" clears it. Back in whatever project you're actually working in, running Import Queued Details reads that file, copies the detail's content in from Details Library.rvt, places it on the requested sheet near where you dropped it (Revit centers the viewport there, same as placing any view by hand — expect a small nudge into final position), and trims the request off the queue. Link the folder here the same way as the Rebar Shape Designer's "Link export folder" (File System Access API, Chrome/Edge only); "Re-check now" re-reads the database and your pending requests without waiting for the next page load. For grabbing several details at once, "Add to cart" on any card's modal builds up a shopping cart (shown at the bottom, with an "In cart" badge on each card) — set the project once there and each item defaults to a sheet matching its own sheet type (Foundation to a foundation sheet, Roof to a roof sheet, and so on), editable per item if the guess is wrong or you'd rather send it elsewhere; "Send cart to Revit…" then auto-arranges each sheet's own group of items onto it in a grid and queues them all in one step instead of placing them one at a time. Open a card's modal and use ←/→ (or the arrows beside it) to step through whatever's currently filtered without closing back to the grid first. Standard note blocks work the same way: select the text notes to keep together in Revit, run Save Notes Bundle, give it a title, and it lands in the library tagged "General Notes" — searchable and placeable through the exact same pipeline as any detail. Running it again with the same title updates that bundle instead of making a duplicate.
